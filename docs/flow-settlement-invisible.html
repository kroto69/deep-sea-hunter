0.Setup — sekali sajaSUDAH

YANG USER LIHAT
  • Connect wallet (Meteor / MyNearWallet / HERE) → verify, sign 1 pesan
  • Tombol ENABLE INVISIBLE SETTLEMENT → approve 1 kali di wallet
  • Storage deposit 1 kali (0,009 NEAR)
  • Auto-mint: tidak ada aksi pemain — tombol VERIFY WALLET · ENABLE AUTO-MINT
DI BELAKANG LAYAR
  • Wallet terikat ke akun game (players.wallet_account)
  • Function Call key ditambah ke akun user — scope: kontrak merchant, method mint_catch / mt_transfer / mt_batch_transfer, allowance 0,25 NEAR (gas saja)
  • Operator: AUTO_MINT_ENABLED + kunci owner di ~/.near-credentials (tidak pernah masuk repo)
  • Storage didaftarkan di kontrak merchant
Ini satu-satunya setup yang terlihat. Setelah ini tidak ada popup lagi.

1.Dive & catchSUDAH

YANG USER LIHAT
  • Dive → tembak → “CAUGHT Clownfish”. Sudah, itu saja.
DI BELAKANG LAYAR

  • Populasi habitat −1, ikan masuk inventory

2.Mint — tanpa sadar, dua jalurA LIVE DI V2 · B BUTUH REDEPLOY

YANG USER LIHAT
  • Tidak ada apa-apa. Di tab chain cuma tertulis status auto-mint + “last catch settled · hash…”.
JALUR A — OPERATOR AUTO-MINT (server)
  • Setelah COMMIT, hunts.js → mintReceipt → mint_asset pakai kunci owner
  • Token fish:catch-{receipt} + 1 purchase order → token_id ditulis
  • Live di v2 Testnet (mint terverifikasi)
JALUR B — SESSION KEY (browser)
  • Frontend minta tanda tangan server: POST /api/near/receipt-signature
  • Panggil mint_catch pakai session key → token fish:{receipt}
  • Lalu POST /api/near/record-mint: server cek mt_balance_of → token_id ditulis
  • Lokal saja — v2 yang live tidak punya mint_catch, butuh redeploy
Penjaga: token_id sudah terisi → jalur lain skip. Satu receipt = satu token. Kalau record gagal (RPC mati), receipt antre sebagai “minted” dan cuma record-nya diulang pas buka game lagi.

3.Sell ke merchant (CR)SUDAH (OFF-CHAIN) · TRANSFER BELUM

YANG USER LIHAT
  • Klik SELL → +CR. Sudah.
DI BELAKANG LAYAR
  • quote() / sell() menolak receipt yang sudah ter-mint (catch_minted_onchain) dan yang sedang listing (receipt_listed)
  • CR pindah merchant → player (ledger Postgres, off-chain); stok merchant +1, demand −1
  • Transfer token on-chain (mt_transfer via session key) belum dibangun — slice 3
Jalur lama tetap ada terpisah: sell di tab NEAR pakai accept_purchase_order + klaim NEAR, perlu sign wallet. Itu bukan jalur invisible.

6.Tick harga + Fast ForwardSUDAH

YANG USER LIHAT

  • Fast Forward: simulasi lokal, tidak menyentuh DB/chain

7.Withdraw CR → NEAR — di sinilah user “ketemu” chainBELUM DIPUTUSKAN

YANG USER LIHAT
  • Layar withdraw → pilih jumlah CR → NEAR masuk wallet.
DI BELAKANG LAYAR
  • CR dibakar (off-chain) → NEAR dikirim dari treasury
  • Rate CR→NEAR + sumber NEAR belum diputuskan (konversi agent 1 CR = 0,0005 NEAR sudah ada di code, tapi flow WD-nya belum)
Yang perlu diingat:
  • Guest tanpa wallet tetap main off-chain penuh — tidak ada akun NEAR untuk dituju tokennya.
  • Session key tidak bisa pindah NEAR, panggil kontrak lain, atau attach > 1 yocto. Allowance habis → grant ulang sekali.
  • Kontrak live: dsh-merchant-v2.deepfish-owner.testnet (code hash 8PjySGU8…). WASM lokal hasil merge (SHA 86fbc4ad…) punya mint_catch — butuh redeploy sebelum jalur session-key jalan on-chain.
  • Sisa jujur: client yang dimodifikasi bisa skip record-mint; rapat penuh butuh cek on-chain di dalam sell() (belum dibangun).
  • Untuk juri: makin bagus invisible-nya, makin tidak ada yang kelihatan — yang ditunjukin itu riwayat hash di tab chain.
