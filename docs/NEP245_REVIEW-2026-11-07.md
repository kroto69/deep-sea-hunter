# NEP-245 review — merchant contract (local source, 2026-11-07)

**Verdict: DO NOT CLAIM NEP-245 COMPLIANCE.** The local merged source implements
the NEP-245 core plus the Metadata and Enumeration extensions (35 of 42
requirements PASS), but the optional Approval Management extension is absent
(1 FAIL), 4 requirements still need a Testnet runtime check (UNPROVEN), and
the deployed v2 contract is an older build without `mint_catch` — so no
compliance claim attaches to anything live today.

## Blockers for any compliance claim

1. **Approval Management is missing (row 29).** It is an optional
   extension, so a narrow "NEP-245 core" claim is not blocked by it — but
   a broad "NEP-245 compliant" claim is, and the gap must be disclosed in
   any case. No delegated-transfer flow (marketplace trading on a user's
   behalf) can work against this contract.
2. **Four UNPROVEN rows (4, 6, 14, 36).** Each needs a Testnet runtime
   check (see below). A compliance claim cannot rest on unit tests alone
   for cross-contract and callback behaviour.
3. **The deployed contract is not the reviewed code.** v2
   (`6dd52d11…`) has no `mint_catch`/`settlement_key`; the reviewed local
   build (`86fbc4ad…`) is undeployed. Nothing live can carry a claim for
   this source until a redeploy happens and the new code hash is recorded
   and re-verified.
4. **Borsh schema change.** The struct gained `settlement_key` and
   `used_receipts` (L:35–36). Redeploying over live state risks
   corruption; prefer a fresh deploy, and ship the
   `storage_balance_of` `{id}` → `{account_id}` server change in the same
   release (row 33).
5. **Stricter-than-spec behaviours must be disclosed, not hidden.** Batch
   cap 10, empty-batch and duplicate-ID rejections, self-transfer
   rejection, receiver-must-be-registered, 0-amount rejection, 0-deposit
   rejection, ignored `force` in `storage_unregister`. None of these is a
   spec violation (the spec is silent on each), but a spec-conforming
   caller could reasonably expect them to work, so they need
   interoperability testing and documentation before any claim.
6. **The `withdraw_proceeds` evidence is incomplete.** The proof doc
   (`docs/ONCHAIN_ECONOMY_PROOF.md`) contradicts itself: the v2 table says
   "withdraw_proceeds is not tested yet", while the auto-mint section
   describes a UI sale+withdraw with `paid_out` 0.009 NEAR but gives **no
   transaction hash for the withdraw call itself**. Separately, the owner
   reported on 2026-11-07 that "wd + sell" were tested on-chain on the
   newest branch — that report is **unverified**: no tx hash, no contract
   account, and no code hash have been supplied, and it is not known
   whether the contract was redeployed from this branch. Per
   `docs/DEPLOYMENT.md` §7, "a claim without a hash does not count" — do
   not cite either withdraw claim as evidence until hashes + contract
   account + code hash are recorded.

## What unit tests prove vs what needs a Testnet runtime check

**Proven by the 59-test suite (re-run 2026-11-07, 59 passed / 0 failed):**
core transfer/balance/supply behaviour; 1-yocto enforcement; owner-only
gates; resolver logic for used/unused/revert/malformed responses; batch
rejections (length, duplicates, >10, empty); metadata views including
missing-token `None`; event shapes for `mt_mint` + `mt_transfer`;
storage min/deposit/withdraw/unregister logic; per-write storage-charging
panics in both directions; `mint_catch` valid/replay/bad-signature/
wrong-catcher/missing-key/owner-only/short-key, including a real ed25519
test vector; withdrawal resolver success/failure restoring the claim.

**Needs a Testnet runtime check (not provable in this sandbox):**
- Multi-token `mt_batch_transfer_call` round-trip against a real receiver
  contract (row 4).
- `mt_resolve_transfer` rejecting a call from a non-self account (row 6).
- Storage callback failure paths with a real failing NEAR transfer, and
  the storage invariant under interleaved operations (row 36).
- Exact on-chain JSON serialisation of the metadata/enumeration views
  (rows 18–25) and a runtime `EVENT_JSON` log assertion from a real
  receipt (rows 15–16). The v1/v2 sale receipts already prove one
  `mt_transfer` log on Testnet, but not the `mt_mint` shape from this
  source.
- A real cross-contract receiver, including a malicious receiver
  (re-entrant transfer attempts, oversized unused arrays, callback
  panics). Sandbox transfer-call suites passed earlier but were not
  re-run in this sandbox and do not cover the deployed bytes.
- The full loop on the redeployed code hash: grant → catch → `mint_catch`
  → sell → `withdraw_proceeds`, plus the 1-yocto rule for function-call
  session keys and the allowance burn rate.
- No access keys on the deployed account (row 14).
- Interoperability of the stricter-than-spec behaviours (row 2 notes,
  rows 30/32 notes) against a spec-conforming caller.

## Non-blocking correctness notes (not compliance issues)

- `mint_internal` inserts into the legacy `assets` map under
  `legacy:{title}` (L:238–258). Two different receipts with the same title
  overwrite each other there; per-receipt balances and supply are
  unaffected, but the `asset()` view can return the wrong (latest) entry.
- `mt_token` always returns `owner_id: None` (row 7). Honest for a
  fungible multi-owner token, but wallets/indexers that expect an owner
  on every token will need `mt_tokens_for_owner` instead.
- Base metadata is one shared `"fish"` base for every token
  (`base_id()`, L:292–293): `base_uri`, `copies`, `symbol`, `icon`,
  `reference` are always `null`. Allowed, but a marketplace that groups
  by base metadata will see a single group.
- `mt_transfer_call` / `mt_batch_transfer_call` attach a fixed 10 Tgas to
  the receiver call and 10 Tgas to the resolve callback (L:287). A
  receiver needing more gas fails the promise and the transfer reverts
  safely — but such receivers are unusable, not just slow.
- The contract is a hybrid: it also implements the FT interface
  (`ft_transfer`, `ft_total_supply`, `ft_balance_of`, `ft_metadata`) via
  `near_contract_standards::FungibleToken`, and `ft_transfer_call`
  intentionally panics as unsupported. That is NEP-141 territory and out
  of scope for this review; it is noted only so the FT surface is not
  mistaken for part of the NEP-245 claim.
- `mt_resolve_transfer`'s written signature in nep-0245.md omits the
  `amounts` parameter from its parameter list while listing it in the
  Arguments section. The code's 5-parameter signature
  `(sender_id, receiver_id, token_ids, amounts, approvals)` matches the
  near-sdk-rs reference implementation; the spec text is internally
  inconsistent here, not the code.

## Recommendations

1. Do not write "NEP-245 compliant" anywhere (README, hackathon form,
   X post) until rows 4, 6, 14, 36 are runtime-verified on the redeployed
   code hash. "NEP-245 core implemented locally, 59 unit tests passing,
   compliance unverified" is the accurate claim.
2. Decide the Approval Management question explicitly: either implement
   it (it is the only FAIL) or record a deliberate "not supported,
   transfers are self-signed only" disclosure. The game does not need it;
   a third-party marketplace might.
3. Close the withdraw evidence gap first — it is cheap: record the tx
   hash(es), contract account, and code hash for the reported on-chain
   wd+sell test, and reconcile the two contradictory statements in
   `docs/ONCHAIN_ECONOMY_PROOF.md`.
4. Add "no access keys on the deployed account" to the redeploy checklist
   in `contracts/merchant/README.md`.
5. Document the stricter-than-spec limits (batch 1–10, no empty/duplicate
   batches, no self-transfer, receiver must be registered) in the contract
   README as interoperability notes.
